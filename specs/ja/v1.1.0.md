# TOML v1.1.0

トムの明瞭で、最小の言語。

By Tom Preston-Werner, Pradyun Gedam, et al.

## 目的

TOMLは最小限の構成ファイル形式であることを目指しており、その形式は明瞭な意味論により読むのが簡単です。TOMLはハッシュテーブルに曖昧さなく対応すべく設計されています。TOMLは幅広い多様な言語におけるデータ構造へ構文解析することが簡単でしょう。

## 前置き

  - TOMLでは大文字と小文字を区別します。

  - 空白とは、タブ (U+0009) もしくはスペース (U+0020) のことです。

  - 改行とは、LF (U+000A) もしくはCRLF (U+000D U+000A) のことです。

  - TOMLファイルは有効にUTF-8で符号化されたユニコードの文書でなければなりません。
    
    とりわけこれが意味するのは、ファイルが *全体として* [充分に形式の整ったコード単位の系列](https://unicode.org/glossary/#well_formed_code_unit_sequence)を形成しなければならないということです。さもなければ、（望ましくは）拒絶されるか、ユニコードの仕様にある通り、不正な形式のバイト綴りはU+FFFDで置き換えなければなりません。

## コメント

ハッシュ記号（`#`）に続けて改行までをコメントとします。 ただし、文字列の内部はコメントになりません。

``` toml
# この行は全てコメントです
key = "value" # これは行の終わりにあるコメントです。
another = "# これはコメントではありません"
```

タブ以外の制御文字（U+0000からU+0008、U+000AからU+001F、U+007F）はコメント中で許可されません。

コメントは、そのファイルの人間の読み手の間での意思疎通に使われるべきです。構文解析器は、コメントの存在（または内容）に基づいて、キーやバリューを改変してはなりません。

## キーとバリューの対

TOML文書の主要な構築部品はキーバリュー対です。

キーは等号の左にあり、バリューは右です。キー名とバリューの周りでは、空白は無視されます。キー、等号、バリューは同じ行になければなりません（ただしバリューには複数行にわたって折り返せるものがあります）。

``` toml
key = "value"
```

バリューは以下の型のうちいずれかでなければなりません。

  - [文字列](#文字列)
  - [整数](#整数)
  - [浮動小数点数](#浮動小数点数)
  - [真偽値](#真偽値)
  - [オフセット付き日時](#オフセット付き日時)
  - [現地の日時](#現地の日時)
  - [現地の日付](#現地の日付)
  - [現地の時刻](#現地の時刻)
  - [配列](#配列)
  - [行内テーブル](#行内テーブル)

未指定のバリューは不正です。

``` toml
key = # 不正
```

キーバリュー対の後には改行（またはEOF）がなければなりません（例外については[行内テーブル](#行内テーブル)を参照）。

``` 
first = "Tom" last = "Preston-Werner" # 不正
```

## キー

キーは、裸のキー、引用符つきキー、ドットつきキーのいずれかにできます。

**裸のキー** には、ASCIIの英字、ASCIIの数字、下線、ダッシュのみを含められます（`A-Za-z0-9_-`）。なお裸のキーは、例えば`1234`のように、ASCIIの数字のみから構成されることが許されますが、常に文字列として解釈されます。

``` toml
key = "value"
bare_key = "value"
bare-key = "value"
1234 = "value"
```

**引用符つきキー** では基本文字列もしくはリテラル文字列のいずれかとまったく同じ規則に従い、ずっと広範なキー名の集合を使うことが許されます。最良慣行としては、絶対に必須のときを除いて裸のキーを使うことです。

``` toml
"127.0.0.1" = "value"
"character encoding" = "value"
"ʎǝʞ" = "value"
'key2' = "value"
'quoted "value"' = "value"
```

裸のキーは非空でなければなりませんが、空の引用符つきキーは許されます（非推奨とはいえ）。複数行文字列を使って引用符つきキーを定義することはできません。

``` toml
= "no key name"           # 不正
"""key""" = "not allowed" # 不正
"" = "blank"              # 有効ですが非推奨
'' = 'blank'              # 有効ですが非推奨
```

**ドットつきキー** は、裸または引用符つきのキーをドットでつなげた連なりです。これにより同様のプロパティをひとまとめにすることができます。

``` toml
name = "Orange"
physical.color = "orange"
physical.shape = "round"
site."google.com" = true
```

JSONのお国言葉では、以下の構造が与えられることでしょう。

``` json
{
  "name": "Orange",
  "physical": {
    "color": "orange",
    "shape": "round"
  },
  "site": {
    "google.com": true
  }
}
```

ドット付きキーが定義するテーブルの詳細については、以下の [テーブル](#テーブル) のセクションを参照してください。

ドットで分割された部分の周りの空白は無視されます。しかしながら、最良慣行としては、余計な空白を一切使わないことです。

``` toml
fruit.name = "banana"       # これが最良慣行
fruit. color = "yellow"     # fruit.colorに同じ
fruit . flavor = "banana"   # fruit.flavorに同じ
```

字下げは空白として扱われ、無視されます。

キーを複数回定義することは不正です。

``` 
# こうはしないこと
name = "Tom"
name = "Pradyun"
```

なお裸のキーと引用符つきキーは等価です。

``` 
# これはうまくいきません
spelling = "favorite"
"spelling" = "favourite"
```

キーが直接に定義済みでない限りはやはり、そこやその内部の名前に書き込んで構いません。

``` toml
# これによりキー「fruit」はテーブルになります。
fruit.apple.smooth = true

# そのためテーブル「fruit」へこのように加えられます。
fruit.orange = 2
```

``` 
# 以下は不正です

# これはfruit.appleのバリューを整数に定義しています。
fruit.apple = 1

# しかしここでは、fruit.appleをテーブルであるかのように扱っています。
# 整数をテーブルと化すことはできません。
fruit.apple.smooth = true
```

ドットつきキーをばらばらの順で定義することは非推奨です。

``` toml
# 有効ですが非推奨

apple.type = "fruit"
orange.type = "fruit"

apple.skin = "thin"
orange.skin = "thick"

apple.color = "red"
orange.color = "orange"
```

``` toml
# こちらの方が推奨されます

apple.type = "fruit"
apple.skin = "thin"
apple.color = "red"

orange.type = "fruit"
orange.skin = "thick"
orange.color = "orange"
```

裸のキーはASCIIの数字のみから成るものにできるため、浮動小数点数のように見えるドットつきキーを書くことは可能ですが、2つの部分からなるドットつきキーなのです。ちゃんとした理由がない限り（たぶんないでしょう）こうはしないこと。

``` toml
3.14159 = "pi"
```

上記のTOMLは以下のJSONに対応します。

``` json
{ "3": { "14159": "pi" } }
```

## 文字列

文字列を記述するには4つの方法があります。基本文字列、複数行基本文字列、リテラル文字列、複数行リテラル文字列です。すべての文字列にはユニコード文字のみが含まれていなければなりません。

**基本文字列** は引用符 (`"`) で囲まれます。あらゆるユニコード文字を使って構いませんが、エスケープしなければならないものは除きます。引用符、バックスラッシュ、タブ以外の制御文字（U+0000からU+0008、U+000AからU+001F、U+007F）がそうです。

``` toml
str = "俺は文字列。\"引用符でくくれる\"。Name\tJos\xE9\nLocation\tSF."
```

利便性のために、いくつかの文字についてはエスケープ綴りの短縮形が用意されています。

``` 
\b         - backspace       (U+0008)     バックスペース
\t         - tab             (U+0009)     タブ
\n         - linefeed        (U+000A)     改行
\f         - form feed       (U+000C)     改ページ
\r         - carriage return (U+000D)     行頭復帰
\e         - escape          (U+001B)     エスケープ
\"         - quote           (U+0022)     引用符
\\         - backslash       (U+005C)     バックスラッシュ
\xHH       - unicode         (U+00HH)     ユニコード
\uHHHH     - unicode         (U+HHHH)     ユニコード
\UHHHHHHHH - unicode         (U+HHHHHHHH) ユニコード
```

あらゆるユニコード文字は`\xHH`か`\uXXXX`か`\UXXXXXXXX`の形でエスケープして構いません。エスケープコードはユニコードの[スカラー値](https://unicode.org/glossary/#unicode_scalar_value)でなければなりません。

留意していただきたいことは、すべてのTOMLの文字列はユニコード文字の系列であって、バイトの系列では *ない* ということです。バイナリデータについては、これらのエスケープコードを使うことを避けてください。その代わりに、16進数の綴りか[Base64](https://en.wikipedia.org/wiki/Base64)のような、外部的なバイナリからテキストへの符号化の戦略が、バイトと文字列の間の変換に推奨されます。

上記に挙がっていない他すべてのエスケープ綴りは予約されています。使われたとき、TOMLはエラーを出すべきです。

ときどき、文章の一節を著す必要があったり（例：翻訳ファイル）、とても長い文字列を複数行に折り返したいことがあります。TOMLではこれが簡単になります。

**複数行基本文字列** はそれぞれの側を3つの引用符で囲まれ、改行が許されます。開始の区切りの直後に続く改行は取り除かれます。他すべての空白と改行文字は手つかずのままに保持されます。

``` toml
str1 = """
Roses are red
Violets are blue"""
```

TOMLの構文解析器は、そのプラットフォームで理にかなう限り好きなように、自由に改行を正規化すべきです。

``` toml
# Unix系では、上記の複数行の文字列はきっとほぼこれと同じことでしょう：
str2 = "Roses are red\nViolets are blue"

# Windows系では、きっとほぼこれと等価なことでしょう：
str3 = "Roses are red\r\nViolets are blue"
```

余計な空白をさしはさむことなく長い文字列を書くためには、「行末のバックスラッシュ」を使うこと。ある行における最後の非空白の文字列がエスケープされない`\`であるとき、次の非空白の文字か閉止の区切りまでの（改行を含む）すべての空白もろとも取り除かれます。基本文字列で有効なすべてのスケープ綴りは複数行基本文字列でも有効です。

``` toml
# 以下の文字列は逐一等価です：
str1 = "とりなくこゑすゆめさませ。"

str2 = """
とりなくこゑす\


  ゆめ\
    さませ。"""

str3 = """\
       とりなく\
       こゑすゆめ\
       さませ。\
       """
```

あらゆるユニコード文字を使って構いませんが、エスケープしなければならないものは除きます。バックスラッシュと、タブ、改行、行頭復帰を除く制御文字（U+0000からU+0008、U+000B、U+000C、U+000EからU+001F、U+007F）がそうです。行頭復帰 (U+000D) は改行の綴りの一部のときのみ許されます。

引用符、または2つの隣接する引用符は、複数行基本文字列のどこにでも書けます。区切りのすぐ内側にも書けます。

``` toml
str4 = """ここには2つ引用符があります：""。単純ですな。"""
# str5 = """ここには3つの引用符があります："""。"""  # 不正
str5 = """ここには3つの引用符があります：""\"。"""
str6 = """ここには15個の引用符があります：""\"""\"""\"""\"""\"。"""


# "これは、" と彼女は言った、"ただの無意味な文よ。"
str7 = """"これは、" と彼女は言った、"ただの無意味な文よ。""""
```

Windowsのパスや正規表現を頻繁に指定していらっしゃる方であるならば、バックスラッシュでエスケープしなければいけないことがすぐに億劫になりエラーの温床となります。そんなときお役に立てるよう、TOMLではエスケープを一切許さないリテラル文字列に対応しています。

**リテラル文字列** は一重引用符で囲まれます。基本文字列のように、単一の行にあらわさなければなりません。

``` toml
# 見ているものがそのまま得られるものです。
winpath  = 'C:\Users\nodejs\templates'
winpath2 = '\\ServerX\admin$\system32\'
quoted   = 'Tom "Dubs" Preston-Werner'
regex    = '<\i\c*\s*>'
```

エスケープがなにもないため、一重引用符により囲まれるリテラル文字列内で一重引用符を書く方法はなにもありません。幸い、TOMLはこの問題を解決する複数行版のリテラル文字列に対応しています。

**複数行リテラル文字列** はそれぞれの側から3つの一重引用符で囲まれており、改行が許されます。リテラル文字列のように、エスケープなんてものはまったくありません。開始の区切りの直後に続く改行は取り除かれます。TOMLの構文解析器は、複数行基本文字列と同じ作法で改行を正規化しなければなりません。

区切りの間にある他すべての内容は改変なしにそのまま解釈されます。

``` toml
regex2 = '''I [dw]on't need \d{2} apples'''
lines  = '''
最初の改行は、
リテラル文字列から取り除かれます。
   他すべての空白は
   保持されます。
'''
```

複数行リテラル文字列内はどこでも1つか2つの一重引用符を書けますが、3つ以上の一重引用符の連続は許可されません。

``` toml
quot15 = '''ここには15個の引用符があります："""""""""""""""'''

# apos15 = '''ここには15個のアポストロフィがあります：''''''''''''''''''  # 不正
apos15 = "ここには15個のポストロフィがあります：'''''''''''''''"

# 'あれは、' と彼女は言った、'やっぱり無意味ね。'
str = ''''あれは、' と彼女は言った、'やっぱり無意味ね。''''
```

タブ以外の制御文字はリテラル文字列で許可されません。

## 整数

整数は、小数部のないキリのよい数です。正数には正符号を前につけて構いません。負数には負符号が前につきます。

``` toml
int1 = +99
int2 = 42
int3 = 0
int4 = -17
```

大きな数値については、可読性を促進するために数字の間に下線を使って構いません。それぞれの下線は少なくとも1つの数字によりそれぞれの側から囲まれていなければなりません。

``` toml
int5 = 1_000
int6 = 5_349_221
int7 = 53_49_221  # インド式命数法での集合化
int8 = 1_2_3_4_5  # 有効ですが非推奨
```

先頭のゼロは許されません。整数値の`-0`と`+0`は有効であり、接頭辞なしのゼロと同一です。

非負整数値は、16進数、8進数、2進数で表しても構いません。これらの形式では、先頭の`+`は許されず、先頭のゼロは（接頭辞の後では）許されます。16進数値は大文字と小文字を区別しません。下線は数字の間では許されます（が接頭辞と値の間ではいけません）。

``` toml
# 接頭辞の`0x`つき16進数
hex1 = 0xDEADBEEF
hex2 = 0xdeadbeef
hex3 = 0xdead_beef

# 接頭辞の`0o`つき8進数
oct1 = 0o01234567
oct2 = 0o755 # Unixのファイルパーミッションに有用

# 接頭辞の`0b`つき2進数
bin1 = 0b11010110
```

実装があらゆる整数の大きさに対応することは自由です。少なくとも64ビットの符号つき整数（-2^63から2^63-1まで）を受け付けて損失なく扱うことが推奨されます。整数が損失なく表せなければ、エラーを投げなければなりません。

## 浮動小数点数

浮動小数点数は（10進整数値と同じ規則に従う）整数部に、小数部および／または指数部が続いたものから成ります。小数部と指数部の両方が存在するなら、小数部は指数部に先行しなければなりません。

``` toml
# 小数部あり
flt1 = +1.0
flt2 = 3.1415
flt3 = -0.01

# 指数部あり
flt4 = 5e+22
flt5 = 1e06
flt6 = -2E-2

# 両方
flt7 = 6.626e-34
```

小数部は小数点に1つ以上の数字が続くものです。

指数部はE（大文字または小文字）の後に整数部（10進整数値と同じ規則に従いますが先頭のゼロを含めて構いません）が続いたものです。

小数点が使われるなら、それぞれの側から少なくとも1つの数字で囲まれていなければなりません。

``` 
# 不正な浮動小数点数
invalid_float_1 = .7
invalid_float_2 = 7.
invalid_float_3 = 3.e+20
```

整数と同様に、可読性を促進するために下線を使って構いません。それぞれの下線は少なくとも1つの数字で囲まれていなければなりません。

``` toml
flt8 = 224_617.445_991_228
```

浮動小数点数の`-0.0`と`+0.0`は有効であり、IEEE 754に従って対応づけられるべきです。

特殊な浮動小数点数値も表せます。常に小文字です。

``` toml
# 無限
sf1 = inf  # 正の無限
sf2 = +inf # 正の無限
sf3 = -inf # 負の無限

# 非数
sf4 = nan  # 実際のsNaN／qNaNの符号化は実装固有
sf5 = +nan # `nan`に同じ
sf6 = -nan # 有効ですが、実際の符号化は実装固有
```

実装があらゆる精度の水準に対応することは自由です。少なくともIEEE 754の長精度値 (binary64) に対応することが推奨されます。

## 真偽値

真偽値はおなじみの字句そのままです。常に小文字です。

``` toml
bool1 = true
bool2 = false
```

## オフセット付き日時

時刻における特定の瞬間を曖昧さなく表すには、[RFC 3339](https://tools.ietf.org/html/rfc3339)で書式化されたオフセットつき日時を使って構いません。

``` toml
odt1 = 1979-05-27T07:32:00Z
odt2 = 1979-05-27T00:32:00-07:00
odt3 = 1979-05-27T00:32:00.5-07:00
odt4 = 1979-05-27T00:32:00.999999-07:00
```

可読性の目的で、（RFC 3339の5.6節で許可されているように）日付と時刻の間のTの区切りをスペースの文字に置き換えて構いません。

``` toml
odt4 = 1979-05-27 07:32:00Z
```

RFC 3339から1つの例外が許可されており、秒を省いて構わないということですが、この場合は`:00`が仮定されます。オフセットは分の直後に続きます。

``` toml
odt5 = 1979-05-27 07:32Z
odt6 = 1979-05-27 07:32-07:00
```

実装は少なくともミリ秒の精度に対応することが要求されます。追加の精度の桁を指定して構いませんが、対応している精度を越えれば、余剰の桁は丸めるのではなく、切り詰めなければなりません。

## 現地の日時

[RFC 3339](https://tools.ietf.org/html/rfc3339)で書式化された日時からオフセットを省くなら、オフセットや等時帯との一切の関連のない所与の日時を表すことになります。追加の情報のない、時刻におけるある瞬間への変換はできません。ある瞬間への変換が、もし必要なら、それは実装固有のものです。

``` toml
ldt1 = 1979-05-27T07:32:00
ldt2 = 1979-05-27T07:32:00.5
ldt3 = 1979-05-27T00:32:00.999999
```

秒は省いて構わず、この場合は`:00`が仮定されます。

``` toml
ldt3 = 1979-05-27T07:32
```

実装は少なくともミリ秒の精度に対応することが要求されます。追加の精度の桁を指定して構いませんが、対応している精度を越えれば、余剰の桁は丸めるのではなく、切り詰めなければなりません。

## 現地の日付

[RFC 3339](https://tools.ietf.org/html/rfc3339)で書式化された日時の日付の部分のみを含めれば、オフセットや等時帯に一切の関連のない全日を表すようになります。

``` toml
ld1 = 1979-05-27
```

## 現地の時刻

[RFC 3339](https://tools.ietf.org/html/rfc3339)で書式化された日時の時刻の部分のみを含めれば、特定の日付や何らかのオフセットや等時帯と一切の関連のないその時刻を表すことになります。

``` toml
lt1 = 07:32:00
lt2 = 00:32:00.5
lt3 = 00:32:00.999999
```

秒は省いて構わず、この場合は`:00`が仮定されます。

``` toml
lt3 = 07:32
```

実装は少なくともミリ秒の精度に対応することが要求されます。追加の精度の桁を指定して構いませんが、対応している精度を越えれば、余剰の桁は丸めるのではなく、切り詰めなければなりません。

## 配列

配列は、角括弧に囲まれた順序つきの値です。空白は無視されます。要素はカンマで分割されます。配列にはキーバリュー対で許されているものと同じデータ型の値を含められます。異なる型の値を混ぜて構いません。

``` toml
integers = [ 1, 2, 3 ]
colors = [ "red", "yellow", "green" ]
nested_arrays_of_ints = [ [ 1, 2 ], [3, 4, 5] ]
nested_mixed_array = [ [ 1, 2 ], ["a", "b", "c"] ]
string_array = [ "all", 'strings', """are the same""", '''type''' ]

# 型の混ざった配列は許されます
numbers = [ 0.1, 0.2, 0.5, 1, 2, 5 ]
contributors = [
  "Foo Bar <foo@example.com>",
  { name = "Baz Qux", email = "bazqux@example.com", url = "https://example.com/bazqux" }
]
```

配列は複数行にわたるようにできます。終端のカンマ（末尾のカンマとも呼ばれます）は配列の最後の値の後において許可されます。どれだけの数の改行やコメントも値、カンマ、閉じ角括弧の前に置けます。配列の値とカンマの間の字下げは空白として扱われ、無視されます。

``` toml
integers2 = [
  1, 2, 3
]

integers3 = [
  1,
  2, # これは大丈夫
]
```

## テーブル

テーブル（ハッシュテーブルや辞書としても知られる）はキーバリュー対の集まりです。見出しによって定義され、角括弧つきで一行を占めます。見出しは配列と見分けがつけられますが、それは配列が値としてしかありえないからです。

``` toml
[table]
```

その下にある、次の見出しまたはEOFまでが、そのテーブルのキーバリュー対です。テーブル内のキーバリュー対は、特定の順序であることが保証されません。

``` toml
[table-1]
key1 = "some string"
key2 = 123

[table-2]
key1 = "another string"
key2 = 456
```

テーブルの命名規則は上述のキーと同じです（[キー](#キー)の定義を参照）。

``` toml
[dog."tater.man"]
type.name = "pug"
```

JSONのお国言葉では、以下の構造が与えられることでしょう。

``` json
{ "dog": { "tater.man": { "type": { "name": "pug" } } } }
```

キーの周囲の空白は無視されます。しかしながら、最良慣行としては、余計な空白を一切使わないことです。

``` toml
[a.b.c]            # これが最良慣行です
[ d.e.f ]          # [d.e.f]と同じ
[ g .  h  . i ]    # [g.h.i]と同じ
[ j . "ʞ" . 'l' ]  # [j."ʞ".'l']と同じ
```

字下げは空白として扱われ、無視されます。

したくなければ、すべての上位テーブルを指定する必要はありません。どうしてあげればいいかTOMLには分かっています。

``` toml
# [x] これらは
# [x.y] 必要
# [x.y.z] ありません
[x.y.z.w] # これが働くようにするにはね

[x] # そのあとで上位テーブルを定義することは大丈夫
```

空のテーブルは許容され、単純に内部にキーとバリューの対が何もないだけです。

キーのように、テーブルを一度ならず二度以上は定義できません。そうするのは不正です。

``` 
# こうはしないこと

[fruit]
apple = "red"

[fruit]
orange = "orange"
```

``` 
# こうもしないこと

[fruit]
apple = "red"

[fruit.apple]
texture = "smooth"
```

テーブルをばらばらの順で定義することは非推奨です。

``` toml
# 有効ですが非推奨
[fruit.apple]
[animal]
[fruit.orange]
```

``` toml
# こちらが推奨されます
[fruit.apple]
[fruit.orange]
[animal]
```

最上位のテーブルは根幹テーブルとも呼ばれ、文書の先頭から始まり、最初のテーブルの見出し（またはEOF）の直前で終わります。 他のテーブルとは異なり、名前がなく、再配置できません。

``` toml
# 最上位テーブルが始まります。
name = "Fido"
breed = "pug"

# 最上位テーブルが終了します。
[owner]
name = "Regina Dogman"
member_since = 1999-08-04
```

ドットつきキーは、最後のキーの部分の前のそれぞれのキーの部分についてテーブルを作成して定義します。そうしたテーブルはすべて、現在の`[テーブル]`の見出しのもとに、またはすべての見出しの前で定義されるなら根幹テーブルにおいて、または1つの行内テーブルにおいて、そのすべてのキーバリュー対が定義されていなければなりません。

``` toml
fruit.apple.color = "red"
# fruit という名前のテーブルを定義します
# fruit.apple という名前のテーブルを定義します

fruit.apple.taste.sweet = true
# fruit.apple.taste という名前のテーブルを定義します
# fruit と fruit.apple はすでに作成されています
```

テーブルは複数回定義できないため、`[テーブル]` の見出しを使用してそのようなテーブルを再定義することはできません。 同様に、`[テーブル]` 形式で既に定義されているテーブルを再定義するためにドットキーを使用することも許可されていません。 ただし、`[テーブル]` 記法は、ドットキーで定義されたテーブル内の副テーブルを定義するために使用できます。

``` toml
[fruit]
apple.color = "red"
apple.taste.sweet = true

# [fruit.apple]        # 不正
# [fruit.apple.taste]  # 不正

[fruit.apple.texture]  # 副テーブルは加えられます
smooth = true
```

## 行内テーブル

行内テーブルは、テーブルを表すためのより簡素な構文を提供します。集合化された入れ子のデータであって、そうしなければすぐ冗長になってしまうようなものにとりわけ有用です。

行内テーブルは波括弧内で、すなわち`{`と`}`とで、完全に定義されたものです。波括弧内では、ゼロ以上のカンマで分割されたキーバリュー対が現れて構いません。キーバリュー対は標準のテーブルにおけるキーバリュー対と同じ形を取ります。すべてのバリューの型が許されており、これには行内テーブルが含まれます。

行内テーブルは同じ行に複数のキーバリュー対を持つか、異なる行に置くことができます。終端のカンマ（末尾のカンマ）は最後のキーバリュー対の後に許可されます。

``` toml
name = { first = "Tom", last = "Preston-Werner" }
point = {x=1, y=2}
animal = { type.name = "pug" }
contact = {
    personal = {
        name = "Donald Duck",
        email = "donald@duckburg.com",
    },
    work = {
        name = "Coin cleaner",
        email = "donald@ScroogeCorp.com",
    },
}
```

上述の行内テーブルは以下の標準のテーブルの定義と同一です。

``` toml
[name]
first = "Tom"
last = "Preston-Werner"

[point]
x = 1
y = 2

[animal]
type.name = "pug"

[contact.personal]
name = "Donald Duck"
email = "donald@duckburg.com"

[contact.work]
name = "Coin cleaner"
email = "donald@ScroogeCorp.com"
```

行内テーブルは完全に自己完結型であり、その中にすべてのキーと副テーブルが定義されます。 キーと副テーブルを波括弧の外側に追加することはできません。

``` toml
[product]
type = { name = "Nail" }
# type.edible = false  # 不正
```

同様に、行内テーブルを使用して、すでに定義されているテーブルにキーや副テーブルを追加することはできません。

``` toml
[product]
type.name = "Nail"
# type = { edible = false }  # 不正
```

## テーブルの配列

まだ説明されていない最後の構文では、テーブルの配列を書けます。これらは、名前を二重括弧で囲んだ見出しを使用して表現できます。その見出しの最初のインスタンスは配列とその最初のテーブル要素を定義し、後続の各インスタンスはその配列内に新しいテーブル要素を作成して定義します。テーブルは、表記された順序で配列に挿入されます。

``` toml
[[product]]
name = "Hammer"
sku = 738594937

[[product]]  # 配列内の空テーブル

[[product]]
name = "Nail"
sku = 284758393

color = "gray"
```

JSONのお国言葉では、以下の構造が得られることでしょう。

``` json
{
  "product": [
    { "name": "Hammer", "sku": 738594937 },
    {},
    { "name": "Nail", "sku": 284758393, "color": "gray" }
  ]
}
```

テーブルの配列への参照は、配列の最後に定義されたテーブル要素を指します。 これにより、直前のテーブル内に副テーブル、さらにはテーブルの副配列を定義できるようになります。

``` toml
[[fruits]]
name = "apple"

[fruits.physical]  # 副テーブル
color = "red"
shape = "round"

[[fruits.varieties]]  # 入れ子になったテーブルの配列
name = "red delicious"

[[fruits.varieties]]
name = "granny smith"


[[fruits]]
name = "banana"

[[fruits.varieties]]
name = "plantain"
```

上記のTOMLは以下のJSONに対応します。

``` json
{
  "fruits": [
    {
      "name": "apple",
      "physical": {
        "color": "red",
        "shape": "round"
      },
      "varieties": [{ "name": "red delicious" }, { "name": "granny smith" }]
    },
    {
      "name": "banana",
      "varieties": [{ "name": "plantain" }]
    }
  ]
}
```

テーブルやテーブルの配列の親が配列の要素なら、その要素に子を定義する前に、その要素が既に定義済みでなければなりません。その順序を逆転させようとする試みには、構文解析時にエラーを出さなければなりません。

``` 
# 不正なTOML文書
[fruit.physical]  # 副テーブルですが、どの親要素に属すべきでしょうか？
color = "red"
shape = "round"

[[fruit]]  # 構文解析器は、「fruit」がテーブルではなく配列であることを
           # 発見するやいなや、エラーを投げなければなりません
name = "apple"
```

静的に定義された配列へ追加する試みは、たとえ配列が空であろうと、構文解析時にエラーを出さなければなりません。

``` 
# 不正なTOML文書
fruits = []

[[fruits]] # 許されません
```

既に確立された配列と同じ名前をもつ普通のテーブルを定義しようとする試みには、構文解析時にエラーを出さなければなりません。普通のテーブルを配列として再定義しようとする試みにも同様に、構文解析時のエラーを出さなければなりません。

``` 
# 不正なTOML文書
[[fruits]]
name = "apple"

[[fruits.varieties]]
name = "red delicious"

# 不正：このテーブルは前のテーブルの配列と競合
[fruits.varieties]
name = "granny smith"

[fruits.physical]
color = "red"
shape = "round"

# 不正：このテーブルの配列は前のテーブルと競合
[[fruits.physical]]
color = "green"
```

適切なところでは行内テーブルを使っても構いません。

``` toml
points = [ { x = 1, y = 2, z = 3 },
           { x = 7, y = 8, z = 9 },
           { x = 2, y = 4, z = 8 } ]
```

## ファイル名の拡張子

TOMLファイルには拡張子`.toml`を使うべきです。

## MIME種別

TOMLファイルをインターネット経由で転送するとき、適切なMIME種別は`application/toml`です。

## ABNF 文法

TOMLの構文の正式な説明が、個別の[ABNFファイル](https://github.com/toml-lang/toml/blob/1.1.0/toml.abnf)として利用できます。
